# ES-Market

AI-powered e-commerce site + internal dashboard for a physical store. Customers browse and order online (pay on delivery/pickup); staff manage the catalog, orders, and an AI-assisted support inbox where every AI-drafted reply is reviewed by an agent before sending.

## Key documents

- [Project-Scope.md](Project-Scope.md) — problem, features, scope decisions, resolved open questions
- [tech-stack.md](tech-stack.md) — stack choices and rationale
- [implementation-plan.md](implementation-plan.md) — phased task breakdown; keep checkboxes updated as tasks complete

## Stack

Bun workspaces monorepo: `client/` (Vite + React + TypeScript), `server/` (Express 5 + TypeScript, runs natively on Bun — no build step), and `core/` (`@es-market/core` — shared TypeScript consumed as source by both, no build step; holds the zod schemas). PostgreSQL via Prisma. OpenAI API for AI features (server-side only, never from the browser). Client UI: Tailwind CSS v4 + shadcn/ui.

## Commands

```sh
bun install              # install all workspace deps (from root)
bun run dev:server       # Express on Bun with --hot, http://localhost:3000
bun run dev:client       # Vite dev server, http://localhost:5173 (proxies /api to :3000)
bun run --cwd server typecheck   # tsc --noEmit
bun run test:e2e         # Playwright E2E: sets up the test DB, then runs specs in e2e/
bun run --cwd client test        # Vitest component tests, single run
bun run --cwd client test:watch  # Vitest component tests, watch mode
```

## Component testing

Component tests use Vitest + React Testing Library, colocated with the component as `*.test.tsx` (e.g. `client/src/pages/UsersPage.tsx` → `client/src/pages/UsersPage.test.tsx`). Config lives in `client/vitest.config.ts` (jsdom environment, `@` alias matching Vite's, setup file at `client/src/test/setup.ts` which loads `@testing-library/jest-dom`).

- Mock `axios` with `vi.mock("axios")` / `vi.mocked(axios, { deep: true })` rather than hitting the network — reset mocks in `beforeEach`.
- Any component using TanStack Query must be rendered through `renderWithQuery` from `client/src/test/render-with-query.tsx` (wraps in a fresh `QueryClientProvider` with retries disabled), not `render` directly.
- Prefer `screen.findBy*` / `waitFor` for async states (loading → success/error) over arbitrary waits.
- For long strings (e.g. testing a `.max()` validation bound past a few hundred characters), use `fireEvent.change` instead of `userEvent.type` — typing key-by-key over 1000+ characters is slow enough to flake against the test timeout under parallel load; `fireEvent.change` sets the value in one go and still exercises the same submit-time validation.
- Run `bun run --cwd client test` after writing or changing component tests, and `bun run --cwd client test:watch` while iterating.

This is separate from Playwright E2E (below) — component tests exercise one component in isolation with mocked I/O; E2E drives the real app end-to-end.

**Component tests are the default for new coverage.** Form validation, dialog open/close and confirm/cancel behavior, loading/error/success states, and request payloads built from mocked axios calls all belong here, not in E2E — they don't need a real server, DB, or filesystem to exercise.

## E2E testing

Playwright E2E tests live in `e2e/` and run against a separate test database (`es_market_test`, never the dev DB).

**Depend on component tests; only run/add E2E tests when absolutely necessary** — reserve it for what actually requires the real stack: real server persistence (a row surviving reload), real filesystem/multer behavior (file-type or size rejection, actual upload/serving), and real auth/session-based routing (role redirects, unauthenticated redirects). If a behavior can be verified by mocking the HTTP layer in a component test, put it there instead and keep the E2E spec to one or two happy-path/integration cases per flow.

**Always delegate writing, extending, or fixing E2E tests to the `e2e-test-writer` subagent** (`.claude/agents/e2e-test-writer.md`) — launch it via the Agent tool rather than editing specs directly in the main conversation. It carries the full setup details (test env, ports, DB lifecycle, auth constraints) and the project's test conventions (locator style, parallel-safety, assertion standards), and it runs the specs it writes. Give it the feature or flow to cover and any acceptance criteria; it handles the rest.

## Authentication

Better Auth (email/password) with the Prisma adapter on PostgreSQL — DB-backed sessions with an opaque cookie ID (no JWT). Staff accounts only: public signup is disabled (`disableSignUp: true`); the admin is seeded and creates other accounts.

- **Server config:** `server/src/lib/auth.ts`. The handler is mounted in `server/src/index.ts` at `app.all("/api/auth/*splat", toNodeHandler(auth))` — this must stay **before** `express.json()`, or Better Auth requests will hang on the consumed body.
- **Roles:** `role` is a Better Auth additional field on `user` (default `Role.AGENT`, `input: false` so clients can't set it); the Prisma `Role` enum is `ADMIN | AGENT`. See the Role enum bullet under Conventions & decisions — never compare against the raw `"ADMIN"`/`"AGENT"` strings.
- **Route protection:** `server/src/middleware/require-auth.ts` exports `requireAuth` (401s if no session, then populates `req.user`/`req.session`) and `requireRole(...roles)` (403s otherwise). Example: `app.get("/api/me", requireAuth, ...)`.
- **Client:** `client/src/lib/auth-client.ts` creates `authClient` from `better-auth/react`, with `inferAdditionalFields` so `role` is typed on the session user (exported as `SessionUser`). Same-origin: Vite proxies `/api` to :3000, so no `baseURL` is set. Use `authClient.useSession()` for auth state, `authClient.signIn.email()` / `authClient.signOut()` for flows; `ProtectedRoute` redirects unauthenticated users to `/admin/login` and takes an optional `roles` prop for role-gated routes (e.g. `<ProtectedRoute roles={[Role.ADMIN]} />` wraps `/admin/users`; disallowed roles are redirected to `/admin`). All staff-facing routes live under `/admin` (see `App.tsx`); `/` is the public storefront. Role-only UI (like the "Users" nav link in `Layout`) checks `user.role === Role.ADMIN`. Client gating is UX only — protect the matching API routes with `requireRole` too.
- **Admin seeding:** `bun run --cwd server seed` (also wired as the Prisma seed) — idempotent, reads `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_NAME`, hashes with `better-auth/crypto` under the `credential` provider. Rejects passwords under 12 chars or the `change-me` placeholder.
- **Env vars** (`server/.env`, see `.env.example`): `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (:3000), `CLIENT_URL` (:5173, listed in `trustedOrigins`), plus the `ADMIN_*` seed vars. `auth.ts` **throws at startup** if `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, or `CLIENT_URL` is missing (no silent fallbacks); `useSecureCookies` is forced on when `NODE_ENV=production`.
- **Rate limiting:** `server/src/middleware/rate-limit.ts` (`express-rate-limit`) — mounted in `index.ts` only when `NODE_ENV=production`: `/api/auth` gets 20 req/IP/15 min (brute-force), `/api/storefront/orders` 10 (order spam), the rest of `/api` 300. Dev and E2E runs are unthrottled. If prod sits behind a proxy, `app.set("trust proxy", ...)` still needs to be configured.

## Conventions & decisions

- **Auth:** DB-backed sessions (Prisma `Session` model, opaque cookie ID) — no JWT, no in-memory sessions. Staff accounts only (ADMIN/AGENT roles), no public signup; admin is seeded. See the Authentication section above for implementation details.
- **Prisma enums:** never compare or assign enum values as raw string literals (`"ADMIN"`, `"DELIVERY"`, …). Server-side Prisma code (routes, `requireRole`, seeds) uses the Prisma-generated enums (`../generated/prisma/client`), which are the source of truth for the DB columns. Everywhere else — client code, shared types, test fixtures — import the mirror const object from `@es-market/core` (the client has no access to the Prisma-generated ones): `Role` in `core/src/schemas/user.ts`, `FulfillmentType` in `core/src/schemas/order.ts`. New Prisma enums that cross the API boundary get the same mirror-const treatment.
- **Languages:** English is primary/required; Arabic, Swahili, French optional with English fallback. Arabic needs RTL. Launch content is entered in English + Arabic only.
- **Cart:** client-side only — `CartProvider`/`useCart` in `client/src/lib/cart.tsx`, persisted to localStorage (`es-market-cart`), no server cart. Items are display snapshots of the product (localized name, price, imageUrl, stock) with quantities clamped to stock; the order API revalidates price and stock server-side, so never trust cart values for money or availability.
- **Checkout:** guest only, no customer accounts in v1. Staff phone-call confirmation (no SMS OTP). Self-delivery, city-only, flat fee with a free-delivery threshold — both are `Setting` rows (see Settings bullet), and `computeDeliveryFee` in `server/src/lib/settings.ts` is the single place that fee logic lives (pickup is always free). The checkout form is `client/src/pages/storefront/CheckoutPage.tsx` (`checkoutFormSchema` = the customer fields; `placeOrderSchema` adds `items`, which the client fills from the cart); the confirmation page reads the placed order from router `location.state` and redirects home if absent.
- **Orders:** non-sequential random order codes for customer status lookup (code + phone) — generated by `server/src/lib/order-code.ts` (8 chars, ambiguous characters excluded), unique column, retry the whole transaction on a P2002 collision (a failed insert aborts the Postgres transaction, so don't retry inside it). `POST /api/storefront/orders` (`server/src/routes/orders.ts`) prices everything from DB rows (never client input), then in a `prisma.$transaction` does a guarded decrement per item (`updateMany` with `stock: { gte: quantity }`, 409 naming the product when `count !== 1` — race-safe stock validation + decrement in one statement) and creates the order with `OrderItem` rows snapshotting `productName`/`unitPrice` (products are editable and soft-deletable; history must show what was charged). Order subtotal/total are **not stored** — derive them from items + `deliveryFee`. Orders are never deleted (no `deletedAt`); they end via `status: CANCELLED`. Staff order endpoints (`GET /api/orders`, `POST /api/orders/:id/{call-attempt,confirm,cancel}`) use `requireAuth` only — order handling is ADMIN **and** AGENT work, unlike the ADMIN-only catalog/user routes; status transitions are race-safe guarded `updateMany`s on the expected current status (`count === 0` → 404 if the order doesn't exist, else 409), and cancel (allowed from RECEIVED/CONFIRMED, zod-validated `CancelReason`) restores stock in the same transaction by incrementing each item's quantity. Phone confirmation: staff log failed calls (`callAttempts`); at `CALL_ATTEMPTS_BEFORE_CANCEL` (3, in `@es-market/core`) the UI (`/admin/orders`) offers cancel-as-unreachable. Customer status lookup is the public `GET /api/storefront/orders/lookup?code=&phone=` (storefront page `/order-status`): `orderLookupSchema` uppercases the code, the server compares phones with spaces/dashes stripped, and a wrong phone returns the **same 404 as an unknown code** — keep codes non-enumerable; the response is the public order shape only (status, item snapshots, derived totals — no customer fields).
- **Admin dashboard overview:** `GET /api/dashboard/stats` (`server/src/routes/dashboard.ts`, ADMIN-only) returns product/order/low-stock counts; low-stock uses the same `stock > 0 && stock < lowStockThreshold` bounds as the client's `getStockStatus` (out-of-stock is a separate bucket, not counted as low-stock) — keep the two in sync if that logic changes. Rendered as `StatCard`s at the top of `DashboardPage.tsx`, each showing a `Skeleton` while its value is `undefined`.
- **Settings:** store-wide config lives in the `Setting` key-value table (`key String @id`, `value Json`) read via `getSettings()` in `server/src/lib/settings.ts`, which merges rows over `DEFAULT_SETTINGS` from `@es-market/core` — no seed needed for new keys, just add a default. Admin-only `GET`/`PUT /api/settings` + admin UI at `/admin/settings` (`client/src/pages/SettingsPage.tsx`); values safe for customers are also exposed on the public `GET /api/storefront/settings`.
- **Inquiries:** channel-agnostic `channel` field from day one (`InquiryChannel` enum, currently just `WEBSITE` — WhatsApp/Instagram are phase 2, added later as additional enum values via an additive migration, not a breaking one). `Inquiry.status` (`OPEN`/`RESOLVED`/`CLOSED`) follows the `Order` pattern: no `deletedAt`, the entity is never deleted, its lifecycle ends via a terminal status instead. There's no separate `queue` column — the inbox queue view derives "my queue"/"unassigned"/"all" from `assignedAgentId` (+ an optional `status` filter), validated by `inquiryListQuerySchema`'s `queue` param (`"mine"` is always resolved server-side from `req.user.id`, never trusted from the client); assignment itself uses the same optional-single-owner-assignment pattern as `Product.assignedAgentId` (nullable FK + relation + index), except **any staff role can be assigned/claim an inquiry**, not just AGENT like Product. `Message.sender` (`CUSTOMER`/`STAFF`) is an explicit enum rather than inferring the author from `authorUserId`'s nullability, and is the extension point future phases will add to (e.g. an `AI_DRAFT` value). Messages are immutable (no `updatedAt`) and cascade-delete with their `Inquiry`. `Inquiry.language` is a plain `String` column (not a Prisma enum — validated against the `LANGUAGES` constant from `core/src/schemas/localized.ts`, same as how `LocalizedName` treats language as plain string keys), captured invisibly from `i18n.resolvedLanguage` when a customer submits (never a visible form field) and surfaced on the staff detail view as a label plus a `dir`/`lang`-aware reply textarea (RTL for Arabic) — a manual affordance only, no translation service. `Inquiry.escalatedAt` is a nullable timestamp **orthogonal to `status`** (not a 4th status value) — an inquiry can be OPEN/RESOLVED and escalated at the same time; escalating reassigns to a specific ADMIN-role user (the one restriction that *is* role-specific) and has no de-escalate action yet.
  - **Planned Phase 6 mapping** (decided ahead of implementation, not yet built): AI classification (6.4) adds four new nullable fields directly on `Inquiry` — `aiTopic`/`aiUrgency` (plain strings validated against a core-side constant, following the `language` precedent, not new Prisma enums), `aiConfidence` (`Float?`), and `aiProductId` (nullable FK to `Product`, mirroring `assignedAgentId`). "Auto-routing to queues" (6.4) does **not** need a real queue column — the classifier just populates `assignedAgentId` itself (e.g. route to whoever's assigned to the concerned product), reusing the existing mine/unassigned/all derivation. AI escalation rules (6.5) reuse `escalatedAt` as a general actor-agnostic "needs a human" signal, but — unlike the staff-facing escalate route — the AI path sets `escalatedAt` **without** touching `assignedAgentId` (it has no specific admin to hand off to; the inquiry just stays/becomes unassigned so any agent can claim it). AI reply drafting (6.6) reuses the already-anticipated `Message.sender = AI_DRAFT` value. Review (6.7) and quality tracking (6.8) should be built together as one field, `Message.draftStatus` (nullable, meaningful only on `AI_DRAFT` rows: `PENDING`/`SENT_UNEDITED`/`SENT_EDITED`/`DISCARDED`), rather than bolted on sequentially; approving-with-edits mints a new `STAFF` message rather than mutating the draft, preserving `Message`'s existing immutability.
  - **Guest/storefront routes** (`server/src/routes/inquiries.ts`, no auth): `POST /api/storefront/inquiries` creates the `Inquiry` + first `CUSTOMER` message (the storefront `ContactPage.tsx` form and the `ChatWidget.tsx` start-form both post here). `GET /api/storefront/inquiries/:id` is the guest thread view — the id is a non-enumerable random UUID (same precedent as order-lookup codes) so no further ownership check is needed, and the response omits customer contact fields/`assignedAgentId`. `POST /api/storefront/inquiries/:id/messages` is the guest follow-up (409 on `CLOSED`, and reopens a `RESOLVED` thread back to `OPEN` — the one case where a message changes status).
  - **Customer chat widget** (`client/src/components/storefront/ChatWidget.tsx`, mounted globally in `StorefrontLayout.tsx`): polls the thread via TanStack Query's `refetchInterval` while open (no SSE anywhere in this codebase — polling is the deliberate, lower-risk choice). Guest identity is just the created `inquiry.id` persisted in `localStorage` (`client/src/lib/inquiry-session.ts`, key `es-market-inquiry-id`) — there are no customer accounts, so a stale/404ing id silently falls back to the start form.
  - **Staff inbox routes** (same file, mounted under plain `/api`, `requireAuth` only — any staff, matching Orders, not ADMIN-only like Products): `GET /inquiries` (list, queue+status filtered), `GET /inquiries/:id` (detail incl. `messages` with `author`), `POST /inquiries/:id/claim` (race-safe guarded `updateMany` on `assignedAgentId: null` — genuinely concurrent, unlike Product's plain `update`), `POST /inquiries/:id/assign` (explicit reassign/unassign, any staff role), `POST /inquiries/:id/escalate` (reassign to a specific ADMIN + stamp `escalatedAt`), `POST /inquiries/:id/messages` (staff reply, `sender: STAFF`, does **not** reopen a `RESOLVED` thread — unlike the guest route), and parameterless `POST /inquiries/:id/{resolve,close,reopen}` transitions — all status transitions use the same guarded-`updateMany` + local `rejectMissingOrConflict`/`respondWithInquiry` pair that mirrors (but doesn't share code with) `orders.ts`'s equivalent helpers.
  - **Staff UI**: `InquiriesPage.tsx` (queue `Tabs` + status `Select`), `InquiriesTable.tsx` (exports `InquiryRow` plus `canClaim`/`canResolve`/`canClose`/`canReopen`/`canEscalate` predicates, same style as `OrdersTable.tsx`'s `canGoOutForDelivery` etc.), `InquiryDetailPage.tsx` (thread bubbles — `STAFF` end-aligned/primary here, the opposite of `ChatWidget`'s customer-end-aligned view since the viewer is staff — an assign `Select` reusing the `""`↔`"unassigned"` mapping from `ProductForm.tsx`, and the escalate `Select`/badge described above).
- **KbArticle:** ADMIN-only CRUD (`server/src/routes/kb-articles.ts`, `client/src/pages/KbArticlesPage.tsx` + `CreateKbArticleDialog.tsx`/`EditKbArticleDialog.tsx`/`DeleteKbArticleDialog.tsx`/`KbArticleForm.tsx`/`KbArticlesTable.tsx`), same tier as Products/Categories/Users — ported directly from the `Category` file set. `title`/`body` are `Json` columns shaped like `LocalizedName`/`LocalizedDescription` (English required for both, unlike Product's fully-optional description — an article with no body isn't a valid entry); `body` allows up to 10,000 chars per language (full prose, not a blurb). `topic` is a single optional plain string, not a taxonomy/relation — enough for Phase 6's classifier to filter/route on later without over-designing now. Soft-deleted (`deletedAt`) like `Product`/`Category`, since Phase 6's FTS index and AI drafting may later reference a specific article by id. One Prisma gotcha specific to this route: `update` treats an `undefined` field as "leave unchanged" (unlike `create`, where it means NULL) — the `PUT` route coerces `topic: topic ?? null` explicitly so clearing a previously-set topic actually persists, instead of silently no-opping.
- **KbArticle full-text search:** four generated `tsvector` columns (`search_en`/`search_ar`/`search_sw`/`search_fr`, added via hand-edited SQL in migration `20260721185241_kb_article_search` — Prisma's schema DSL has no native tsvector support, so `schema.prisma` declares them as `Unsupported("tsvector")?` purely so future migrations don't treat them as drift and propose dropping them; all actual reads go through raw SQL). Each column combines that language's `title` (weight `'A'`) + `body` (weight `'B'`) via `setweight`, falling back to the English field when a translation is missing so an untranslated article is still findable. One column per language (not one combined column with a language discriminant) since a query always knows the customer's language up front (`Inquiry.language`) and only ever searches one column. Postgres ships built-in text search configs for `english`/`arabic`/`french`; **Swahili has no built-in config** and falls back to `'simple'` (tokenize/lowercase only, no stemming) — a documented, accepted quality gap, not a bug. Query path: `server/src/lib/kb-search.ts`'s `searchKbArticles(query, language, limit?)` uses `prisma.$queryRaw`/`Prisma.sql` (Prisma Client can't express `@@`/`tsquery`/`ts_rank`, and `Unsupported` fields aren't selectable through it anyway) — the column name and `regconfig` are only ever taken from a fixed `Record<Language, string>` lookup (never raw request text), while the actual search text always goes through the tagged-template placeholder, never `Prisma.raw`. This is retrieval plumbing for Phase 6.6's AI drafting (per `tech-stack.md`, "Postgres FTS to select candidate articles passed into the prompt, no vector DB until draft quality demands it") — there's a minimal ADMIN-only `GET /api/kb-articles/search?q=&language=` for verification, but deliberately **no search box in `KbArticlesPage.tsx`**, since FTS isn't an admin-facing feature here.
- **Styling:** Tailwind v4 utilities + shadcn components only — no custom CSS files or inline styles. shadcn is set up with the nova preset, neutral base, CSS variables, and RTL enabled (`client/components.json`); add components with `bunx shadcn@latest add <name>` from `client/`. Use theme tokens (`bg-muted`, `text-destructive`, `bg-primary`, …), not hardcoded palette colors. Brand primary is a dark forest green (oklch hue 152, defined in `client/src/index.css`). `DialogContent` (`client/src/components/ui/dialog.tsx`) is capped at `max-h-[calc(100vh-2rem)]` with its content scrolling internally (not the whole popup growing past the viewport) — don't special-case tall dialog content (e.g. long-text fields) per usage, the shared component already handles it. The `Button` is Base UI (no Radix `asChild`); for a navigation link styled as a button use `<Link className={buttonVariants({ … })}>` (see `CartPage.tsx`) — not `render={<Link/>}` + `nativeButton={false}`, which stamps `role="button"` on the anchor and breaks link semantics.
- **AI:** GPT-5 for reply drafting, GPT-5 mini for classification; structured outputs (JSON schema). Every AI reply requires agent approval before sending.
- **Data fetching:** use `axios` (not `fetch`) with TanStack Query (`@tanstack/react-query`) for all client-side API calls — wrap queries in `useQuery`/`useMutation` rather than manual `useEffect`/`useState` fetching. `QueryClientProvider` is set up in `client/src/main.tsx`.
- **Validation:** use `zod` (v4) for data validation on both sides — no hand-rolled validation. Define each schema once in the `core` package (`core/src/schemas/`, exported from `core/src/index.ts` along with its inferred type) and import it from `@es-market/core` in both client and server — never duplicate a schema in `client/` or `server/`. Server routes validate request bodies with the shared schema + `safeParse` (400 with the first issue's message on failure; see `server/src/routes/users.ts`); the client uses the same schema in forms (see the Forms bullet), which keeps error messages identical on both sides. Example: `createUserSchema` in `core/src/schemas/user.ts`. Every free-text string field gets an explicit `.max(...)`, not just a `.min(...)` — e.g. `localizedNameSchema` (`core/src/schemas/localized.ts`, shared by `Product.name`/`Category.name`) caps each language at 200 chars, `localizedDescriptionSchema` at 1000; ID-shaped fields like `categoryId`/`assignedAgentId` in `createProductSchema` also get a generous bound (100) even though they're not user-composed prose, since nothing upstream otherwise limits their length.
- **Forms:** build client forms with React Hook Form + a zod schema via `zodResolver` from `@hookform/resolvers/zod` — no manual `useState` form handling. Reference implementation: the create-user form in `client/src/pages/CreateUserDialog.tsx` (schema-driven validation, inline `text-destructive` field errors, submit wired to a TanStack `useMutation`). For a form that handles both create and edit in one component (schema/mutation/button text switching on whether an entity prop is passed), see `client/src/components/UserForm.tsx` / `ProductForm.tsx`, paired with separate `Create<Entity>Dialog.tsx` / `Edit<Entity>Dialog.tsx` / `Delete<Entity>Dialog.tsx` wrappers (`client/src/pages/`) and an actions column with edit/delete icon buttons in the `<Entity>sTable` (`client/src/components/`). When a schema uses `z.preprocess`/`.transform`, type `useForm` with the exported `…FormInput = z.input<…>` type (e.g. `CreateProductFormInput`, `CheckoutFormInput`, `UpdateSettingsFormInput`), not the `z.infer` type — preprocess makes the input side `unknown`, and the infer type won't match the resolver.
- **Soft delete:** entities that may be referenced elsewhere later (e.g. a future Order referencing Product) are soft-deleted via a nullable `deletedAt DateTime?` column, not hard `DELETE`s — see `User` and `Product` in `schema.prisma`. List queries filter `where: { deletedAt: null }`; the `DELETE` route sets `deletedAt: new Date()` and 404s if the row is already deleted. Only hard-delete an entity if nothing will ever need to reference the deleted row again.
- **Pricing:** `Product.price` is a whole-number `Int` (no decimal/cents subunits) — matches how `stock`/`lowStockThreshold` are already modeled and avoids float-precision issues. Don't introduce cents-based conversion without an explicit decision to do so.
- **List ordering:** list queries order by `createdAt: "desc"` (newest first) unless a feature has a specific reason to differ — see `GET /api/products` in `server/src/routes/products.ts`.
- **Optional single-owner assignment:** an entity assignable to one staff member (e.g. `Product.assignedAgentId`) is a nullable FK on the owned entity — not a join table — mirroring the existing required `categoryId` FK pattern. Reference implementation: `Product.assignedAgentId`/`assignedAgent` in `schema.prisma`, validated in `POST`/`PUT /api/products` the same way `categoryId` is (fetch the target user, 404 `"Agent not found"` if missing, soft-deleted, **or not the expected `Role`** — don't just check existence). The include/select shape stays minimal (`{ id, name }`), not the full user row. On the client, the assignee `Select` (`ProductForm.tsx`) is populated from `GET /api/users` filtered client-side to the target role, with an explicit "Unassigned" option; since shadcn's `Select` can't use a literal empty-string value, the "Unassigned" choice maps to `""` in the form and the shared zod schema preprocesses `"" → undefined` (see `assignedAgentId` in `core/src/schemas/product.ts`) so omitting the field un-assigns rather than validation-failing. The entity's list table gets a corresponding non-sortable column rendering the assignee's name or "Unassigned".
- **File uploads:** local disk only (no S3/cloud storage in v1, per `tech-stack.md`), served publicly and unauthenticated since these are catalog assets a future public storefront will need anyway. Reference implementation: product images (`server/src/lib/uploads.ts` for the directory setup, `server/src/routes/products.ts` for the `multer` config and the `POST /api/<resource>/:id/image` route, mounted alongside a plain `express.static` mount under `/api/uploads` in `server/src/index.ts`). Upload is a **separate endpoint** taking `multipart/form-data`, not folded into the entity's JSON create/edit routes — this keeps those routes' zod schemas and request contracts untouched. `multer`'s `fileFilter` + `limits.fileSize` enforce type/size restrictions server-side; wrap the `multer` middleware to translate `MulterError` into the same `400 { error: message }` shape other routes use. Uploaded files live under `server/uploads/<resource>/`, gitignored except for a committed `.gitkeep`.
