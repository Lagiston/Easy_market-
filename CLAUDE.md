# Halatu

AI-powered e-commerce site + internal dashboard for a physical store. Customers browse and order online (pay on delivery/pickup); staff manage the catalog, orders, and an AI-assisted support inbox where every AI-drafted reply is reviewed by an agent before sending.

## Key documents

- [Project-Scope.md](Project-Scope.md) — problem, features, scope decisions, resolved open questions
- [tech-stack.md](tech-stack.md) — stack choices and rationale
- [implementation-plan.md](implementation-plan.md) — phased task breakdown; keep checkboxes updated as tasks complete

## Stack

Bun workspaces monorepo: `client/` (Vite + React + TypeScript), `server/` (Express 5 + TypeScript, runs natively on Bun — no build step), and `core/` (`@es-market/core` — shared TypeScript consumed as source by both, no build step; holds the zod schemas). PostgreSQL via Prisma. Vercel AI SDK (OpenAI provider) for AI features (server-side only, never from the browser). Client UI: Tailwind CSS v4 + shadcn/ui.

## Commands

```sh
bun install              # install all workspace deps (from root)
bun run dev:server       # Express on Bun with --hot, http://localhost:3000
bun run dev:client       # Vite dev server, http://localhost:5173 (proxies /api to :3000)
bun run --cwd server typecheck   # tsc --noEmit
bun run test:e2e         # Playwright E2E: sets up the test DB, then runs specs in e2e/
bun run --cwd client test        # Vitest component tests, single run
bun run --cwd client test:watch  # Vitest component tests, watch mode
```

## Component testing

Component tests use Vitest + React Testing Library, colocated with the component as `*.test.tsx` (e.g. `client/src/pages/UsersPage.tsx` → `client/src/pages/UsersPage.test.tsx`). Config lives in `client/vitest.config.ts` (jsdom environment, `@` alias matching Vite's, setup file at `client/src/test/setup.ts` which loads `@testing-library/jest-dom`).

- Mock `axios` with `vi.mock("axios")` / `vi.mocked(axios, { deep: true })` rather than hitting the network — reset mocks in `beforeEach`.
- Any component using TanStack Query must be rendered through `renderWithQuery` from `client/src/test/render-with-query.tsx` (wraps in a fresh `QueryClientProvider` with retries disabled), not `render` directly.
- Prefer `screen.findBy*` / `waitFor` for async states (loading → success/error) over arbitrary waits.
- For long strings (e.g. testing a `.max()` validation bound past a few hundred characters), use `fireEvent.change` instead of `userEvent.type` — typing key-by-key over 1000+ characters is slow enough to flake against the test timeout under parallel load; `fireEvent.change` sets the value in one go and still exercises the same submit-time validation.
- Run `bun run --cwd client test` after writing or changing component tests, and `bun run --cwd client test:watch` while iterating.

This is separate from Playwright E2E (below) — component tests exercise one component in isolation with mocked I/O; E2E drives the real app end-to-end.

**Component tests are the default for new coverage.** Form validation, dialog open/close and confirm/cancel behavior, loading/error/success states, and request payloads built from mocked axios calls all belong here, not in E2E — they don't need a real server, DB, or filesystem to exercise.

## E2E testing

Playwright E2E tests live in `e2e/` and run against a separate test database (`es_market_test`, never the dev DB).

**Depend on component tests; only run/add E2E tests when absolutely necessary** — reserve it for what actually requires the real stack: real server persistence (a row surviving reload), real filesystem/multer behavior (file-type or size rejection, actual upload/serving), and real auth/session-based routing (role redirects, unauthenticated redirects). If a behavior can be verified by mocking the HTTP layer in a component test, put it there instead and keep the E2E spec to one or two happy-path/integration cases per flow.

**Always delegate writing, extending, or fixing E2E tests to the `e2e-test-writer` subagent** (`.claude/agents/e2e-test-writer.md`) — launch it via the Agent tool rather than editing specs directly in the main conversation. It carries the full setup details (test env, ports, DB lifecycle, auth constraints) and the project's test conventions (locator style, parallel-safety, assertion standards), and it runs the specs it writes. Give it the feature or flow to cover and any acceptance criteria; it handles the rest.

## Authentication

Better Auth (email/password) with the Prisma adapter on PostgreSQL — DB-backed sessions with an opaque cookie ID (no JWT). This section covers the **staff** instance: public signup is disabled (`disableSignUp: true`); the admin is seeded and creates other accounts. See **Customer accounts** below for the separate, second Better Auth instance customers use.

- **Server config:** `server/src/lib/auth.ts`. The handler is mounted in `server/src/index.ts` at `app.all("/api/auth/*splat", toNodeHandler(auth))` — this must stay **before** `express.json()`, or Better Auth requests will hang on the consumed body.
- **Roles:** `role` is a Better Auth additional field on `user` (default `Role.AGENT`, `input: false` so clients can't set it); the Prisma `Role` enum is `ADMIN | AGENT`. See the Role enum bullet under Conventions & decisions — never compare against the raw `"ADMIN"`/`"AGENT"` strings.
- **Route protection:** `server/src/middleware/require-auth.ts` exports `requireAuth` (401s if no session, then populates `req.user`/`req.session`) and `requireRole(...roles)` (403s otherwise). Example: `app.get("/api/me", requireAuth, ...)`.
- **Client:** `client/src/lib/auth-client.ts` creates `authClient` from `better-auth/react`, with `inferAdditionalFields` so `role` is typed on the session user (exported as `SessionUser`). Same-origin: Vite proxies `/api` to :3000, so no `baseURL` is set. Use `authClient.useSession()` for auth state, `authClient.signIn.email()` / `authClient.signOut()` for flows; `ProtectedRoute` redirects unauthenticated users to `/admin/login` and takes an optional `roles` prop for role-gated routes (e.g. `<ProtectedRoute roles={[Role.ADMIN]} />` wraps `/admin/users`; disallowed roles are redirected to `/admin`). All staff-facing routes live under `/admin` (see `App.tsx`); `/` is the public storefront. Role-only UI (like the "Users" nav link in `Layout`) checks `user.role === Role.ADMIN`. Client gating is UX only — protect the matching API routes with `requireRole` too.
- **Admin seeding:** `bun run --cwd server seed` (also wired as the Prisma seed) — idempotent, reads `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_NAME`, hashes with `better-auth/crypto` under the `credential` provider. Rejects passwords under 12 chars or the `change-me` placeholder.
- **Env vars** (`server/.env`, see `.env.example`): `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (:3000), `CLIENT_URL` (:5173, listed in `trustedOrigins`), plus the `ADMIN_*` seed vars. `auth.ts` **throws at startup** if `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, or `CLIENT_URL` is missing (no silent fallbacks); `useSecureCookies` is forced on when `NODE_ENV=production`.
- **Rate limiting:** `server/src/middleware/rate-limit.ts` (`express-rate-limit`) — mounted in `index.ts` only when `NODE_ENV=production`: `/api/auth` and `/api/customer-auth` each get 20 req/IP/15 min (brute-force/signup-spam, same `authLimiter`), `/api/storefront/orders` 10 (order spam), `/api/customer/orders/link-by-phone` 10 (`linkOrdersLimiter` — each request is a phone-number guess that, if it hits, permanently transfers a stranger's order to the requester's account; `requireCustomerAuth` alone doesn't stop one account from iterating many numbers), the rest of `/api` 300. Dev and E2E runs are unthrottled. If prod sits behind a proxy, `app.set("trust proxy", ...)` still needs to be configured.
- **Security headers:** `helmet()` is mounted as the very first middleware in `server/src/index.ts` (before rate limiters and the Better Auth handlers), using its defaults unmodified — this is an API-only server with no HTML views, so the default CSP/HSTS/frame-ancestors/nosniff set is safe as-is with nothing to tune.

## Customer accounts

A second, fully separate Better Auth instance from the staff one above — not a third `Role` value on the staff `User` table. The staff instance has public signup deliberately disabled and `role` is a staff-only concept (`ADMIN | AGENT`, exhaustively checked throughout `requireRole`/agent-assignment dropdowns/etc.); reusing it for customers would mean either weakening that signup gate or bolting an unrelated concept onto every place that treats `Role` as exhaustive. Building phase-2 of the guest-checkout decision in `Project-Scope.md` ("guest checkout for v1 — customer accounts are a phase 2 candidate"), scoped to what that doc flagged as the actual point of accounts: order history, not just a login.

- **Server config:** `server/src/lib/customer-auth.ts` — `emailAndPassword: { enabled: true }` with signup left on (the opposite of the staff instance), pointed at its own `Customer`/`CustomerSession`/`CustomerAccount`/`CustomerVerification` Prisma models via `modelName`, mounted at `basePath: "/api/customer-auth"` with `advanced.cookiePrefix: "es-market-customer"` so its routes/cookies never collide with the staff instance's `/api/auth`/`better-auth.*`. **Gotcha found live:** Better Auth's internal FK field name back to the user is always `userId` regardless of what the user model is called — since these Prisma models name that column `customerId` (matching this feature's own naming), `session`/`account` both need an explicit `fields: { userId: "customerId" }` override or every write 500s with a confusing "Argument `customer` is missing" Prisma error. The handler is mounted the same way as the staff one, `app.all("/api/customer-auth/*splat", toNodeHandler(customerAuth))`, also **before** `express.json()`.
- **No email flows:** no email-sending infrastructure exists anywhere in this repo. `requireEmailVerification` is left at its default `false` (signup works immediately, no verification step — Better Auth's default, confirmed via docs), and there's no self-service password reset. A customer who forgets their password has no recovery path — a known v1 gap, not solved.
- **`Customer` has no `deletedAt`:** unlike `User`/`Product`, there's no account-deactivation flow being built, so a soft-delete column would be speculative — add it if/when that flow exists.
- **Route protection:** `server/src/middleware/require-customer-auth.ts` exports `requireCustomerAuth`, mirroring `requireAuth` exactly but populating `req.customer`/`req.customerSession` from `customerAuth.api.getSession`.
- **Client:** `client/src/lib/customer-auth-client.ts` creates `customerAuthClient` (`createAuthClient({ basePath: "/api/customer-auth" })`, exported session-user type `CustomerSessionUser`). `CustomerProtectedRoute` (mirrors `ProtectedRoute` but redirects to `/account/login` instead of `/admin/login`, and renders no chrome of its own — it nests *inside* `StorefrontLayout`'s routes rather than wrapping a separate layout, since account pages want the normal storefront header/footer) wraps `/account`, `/account/profile`, `/account/orders`, and `/account/wishlist` in `App.tsx`; `/account/login` and `/account/signup` are public storefront routes. `SiteHeader.tsx` (the storefront nav header, see the Styling section below) shows a "Sign in" link (→ `/account/login`) or the customer's name (→ `/account`) based on `customerAuthClient.useSession()`.
- **Profile fields (mobile, gender, region, profile picture)**: `Customer` gained `mobile`/`gender`/`region` columns (`Gender` a new Prisma enum — `MALE | FEMALE | PREFER_NOT_TO_SAY` — mirrored in `core/src/schemas/customer.ts` per the Prisma-enums convention below) plus reuse of Better Auth's own built-in `image` column (previously present but unused) for the avatar URL. The three new text/enum fields are registered as Better Auth `user.additionalFields` on **both** `customer-auth.ts` (`input: true` — unlike staff `role`'s `input: false`, since these are customer-settable) and `customer-auth-client.ts` (`inferAdditionalFields`, `required: false` on both sides so `CustomerSessionUser` and the sign-up call stay correctly optional) — writes go straight through Better Auth's own `/update-user` endpoint (`customerAuthClient.updateUser({ name, mobile, gender, region })`), no hand-written Express route needed for them, same "let Better Auth own it" precedent as sign-up/sign-in. `updateCustomerProfileSchema` (`core/src/schemas/customer.ts`) is client-side validation only for the same reason `customerSignUpSchema` is; `mobile`/`gender`/`region` are each `z.preprocess`'d from `""` to `undefined` (blank field → "leave unchanged" is wrong here — see the null-clearing note below) using the same convention as `assignedAgentId`. **Gotcha found live:** Better Auth's additionalFields write `undefined` as "leave unchanged" (mirroring Prisma's own `update` semantics) — clearing a previously-set field requires sending an explicit `null`, but the client's inferred type for a `type: "string"` additionalField is plain `string` with no `null` variant even when `required: false`, so `AccountProfilePage.tsx`'s submit handler casts the payload (`as Parameters<typeof customerAuthClient.updateUser>[0]`) to pass `null` — the server's Prisma write accepts it correctly at runtime regardless of the client typing gap. **Second gotcha found live:** `customerAuthClient.useSession()` is backed by Better Auth's own internal store, not this app's TanStack QueryClient, and only auto-refreshes on Better Auth's own endpoints — the hand-written avatar upload/delete routes below don't trigger it, so `CustomerAvatarUpload.tsx` takes an `onChanged` callback wired to `useSession()`'s own `refetch()` rather than any query invalidation. Avatar upload/delete (`POST`/`DELETE /customer/profile/avatar`, `server/src/routes/customer.ts`) is a single-file variant of the product-image upload pattern (`server/src/routes/products.ts`) — `multer.memoryStorage()` + `file-type` magic-byte validation, uploaded to Cloudinary under the `"customers"` folder via `uploadImageBuffer` (see the File uploads convention bullet below) — but **replaces** rather than appends: on a successful upload the customer's previous avatar (if any) is best-effort deleted from Cloudinary and `Customer.image` is overwritten, since this is one avatar, not a gallery.
- **Order linking is soft/optional auth** — a pattern used nowhere else in this codebase (everything else is a hard `requireAuth`/`requireRole` gate). `POST /api/storefront/orders` stays public/unauthenticated either way; it just additionally calls `customerAuth.api.getSession(...)` inline and attaches `customerId` (nullable FK on `Order`, `@@index`ed) when a valid customer session cookie happens to be present, guest orders unaffected. `customerName`/`customerPhone`/`address` stay point-in-time snapshots regardless (same precedent as `OrderItem.productName`/`unitPrice`), so `customerId` is purely an additional identity link, not a replacement.
- **Checkout prefill + save-to-profile (`Customer.address`, `CheckoutPage.tsx`)**: `Customer` gained a fourth profile field, `address` (plain uncapped `String?`, same shape as `Order.address`, added to `updateCustomerProfileSchema`/both `additionalFields` blocks exactly like `mobile`/`gender`/`region` above — editable on `/account/profile` alongside them). `CheckoutPage.tsx` is otherwise still guest-first (`POST /api/storefront/orders` is untouched, still always prices/snapshots from the request body per the bullet above), but now calls `customerAuthClient.useSession()` and, once resolved, prefills `customerName`/`customerPhone`/`address` from the saved profile — a one-directional convenience default (same precedent as `ProductReviews.tsx`'s `authorName` prefill), each field only set if it's still at its untouched empty default so a buy-now flow or something the customer already typed is never clobbered. This is the **first form other than the profile editor itself that writes back to `Customer`**: an explicit, unchecked-by-default "Save this address to my profile" `Checkbox` (rendered only when signed in and `fulfillmentType === DELIVERY`) — checking it fires `customerAuthClient.updateUser({ name, mobile, address })` with the *submitted* (possibly customer-edited) values in the order mutation's `onSuccess`, never automatic/silent, same philosophy as `link-by-phone` above. That write-back is a second, independent, best-effort request — it doesn't block or gate order placement (which has already succeeded by the time it fires), and a failure (`{ error }` in Better Auth's response, or a rejected promise) shows a non-blocking `toast.error` rather than affecting the confirmation navigation.
- **`GET /api/customer/orders`** (`server/src/routes/customer.ts`, `requireCustomerAuth`) — the signed-in "My orders" list, filtered to `customerId: req.customer.id`. Shares a `serializePublicOrder`/`orderWithItems` helper (exported from `server/src/routes/orders.ts`) with the guest `GET /storefront/orders/lookup` route, since both return the identical customer-safe order shape (no `customerName`/`customerPhone`/`address`/`customerId` — that's `serializeOrder`, the separate staff-only version in the same file).
- **Claiming past guest orders**: `POST /api/customer/orders/link-by-phone` (`requireCustomerAuth`) lets a signed-in customer voluntarily link guest orders placed before they had an account — **never automatic/silent**, since a phone number isn't verified proof of ownership; the customer has to explicitly submit the phone they ordered with (`AccountOrdersPage.tsx`'s "Ordered as a guest before?" form). Matches `customerPhone` normalized the same way as the guest lookup route (reuses `normalizePhone`, exported from `orders.ts`) over all still-`customerId: null` orders — v1 simplification, matched in JS rather than a normalized SQL comparison (same "fine at this store's scale" tradeoff already accepted for the tag-flattening and AI-classification-catalog queries elsewhere). The final `updateMany`'s `where` re-checks `customerId: null`, so it can only ever claim still-unclaimed orders — one customer can't steal an order another account already linked, even if they know the same phone number. Rate-limited in production (see the Rate limiting bullet above) since a signed-in account could otherwise iterate phone numbers to permanently hijack strangers' orders. Returns `{ linkedCount }`; the client shows a pluralized "Linked N orders" message and refetches `/api/customer/orders` only when `linkedCount > 0`.
- **Explicitly out of scope for this pass:** cart (confirmed client-only/localStorage, no server sync anywhere), and inquiries/chat (their own independent guest-identity mechanism via `inquiry-session.ts`, untouched). Checkout-form prefill from the account profile was flagged out of scope in the original pass but has since been built — see the checkout-prefill bullet below.

## Conventions & decisions

- **Auth:** DB-backed sessions (Prisma `Session` model, opaque cookie ID) — no JWT, no in-memory sessions. Staff accounts only (ADMIN/AGENT roles), no public signup; admin is seeded. See the Authentication section above for implementation details.
- **Prisma enums:** never compare or assign enum values as raw string literals (`"ADMIN"`, `"DELIVERY"`, …). Server-side Prisma code (routes, `requireRole`, seeds) uses the Prisma-generated enums (`../generated/prisma/client`), which are the source of truth for the DB columns. Everywhere else — client code, shared types, test fixtures — import the mirror const object from `@es-market/core` (the client has no access to the Prisma-generated ones): `Role` in `core/src/schemas/user.ts`, `FulfillmentType` in `core/src/schemas/order.ts`. New Prisma enums that cross the API boundary get the same mirror-const treatment.
- **Languages:** English is primary/required; Arabic, Swahili, French optional with English fallback. Arabic needs RTL. Launch content is entered in English + Arabic only.
- **Cart:** client-side only — `CartProvider`/`useCart` in `client/src/lib/cart.tsx`, persisted to localStorage (`es-market-cart`), no server cart. Items are display snapshots of the product (localized name, price, imageUrl, stock) with quantities clamped to stock; the order API revalidates price and stock server-side, so never trust cart values for money or availability. `clampQuantity` treats zero stock as a special case (returns `0`, not `1`) — `addItem`/`updateQuantity` remove the item outright when this happens rather than storing a zero-quantity entry, since a stray zero-quantity item would violate the same `quantity > 0` invariant `loadCart` already enforces when validating a persisted cart from `localStorage`.
- **Checkout:** guest-first — no account is required to order (a v1 decision, since superseded by customer accounts as a phase-2 addition; see the checkout-prefill bullet under **Customer accounts** for how a signed-in customer's saved details are now optionally used). Staff phone-call confirmation (no SMS OTP). Self-delivery, city-only, flat fee with a free-delivery threshold — both are `Setting` rows (see Settings bullet), and `computeDeliveryFee` in `server/src/lib/settings.ts` is the single place that fee logic lives (pickup is always free). The checkout form is `client/src/pages/storefront/CheckoutPage.tsx` (`checkoutFormSchema` = the customer fields; `placeOrderSchema` adds `items`, which the client fills from the cart); the confirmation page reads the placed order from router `location.state` and redirects home if absent.
- **Orders:** non-sequential random order codes for customer status lookup (code + phone) — generated by `server/src/lib/order-code.ts` (8 chars, ambiguous characters excluded), unique column, retry the whole transaction on a P2002 collision (a failed insert aborts the Postgres transaction, so don't retry inside it). `POST /api/storefront/orders` (`server/src/routes/orders.ts`) prices everything from DB rows (never client input), then in a `prisma.$transaction` does a guarded decrement per item (`updateMany` with `stock: { gte: quantity }`, 409 naming the product when `count !== 1` — race-safe stock validation + decrement in one statement) and creates the order with `OrderItem` rows snapshotting `productName`/`unitPrice` (products are editable and soft-deletable; history must show what was charged). Order subtotal/total are **not stored** — derive them from items + `deliveryFee`. Orders are never deleted (no `deletedAt`); they end via `status: CANCELLED`. `Order.customerId` (nullable) links to a signed-in customer's account when present — see **Customer accounts** below for how/when it's set. Staff order endpoints (`GET /api/orders`, `POST /api/orders/:id/{call-attempt,confirm,cancel}`) use `requireAuth` only — order handling is ADMIN **and** AGENT work, unlike the ADMIN-only catalog/user routes; status transitions are race-safe guarded `updateMany`s on the expected current status (`count === 0` → 404 if the order doesn't exist, else 409), and cancel (allowed from RECEIVED/CONFIRMED, zod-validated `CancelReason`) restores stock in the same transaction by incrementing each item's quantity. Phone confirmation: staff log failed calls (`callAttempts`); at `CALL_ATTEMPTS_BEFORE_CANCEL` (3, in `@es-market/core`) the UI offers cancel-as-unreachable (a guided `CancelUnreachableOrderDialog` pre-filling `CUSTOMER_UNREACHABLE`) — on both the order list (`OrdersTable.tsx`) and the order detail page (`OrderDetailPage.tsx`); keep the `callAttempts >= CALL_ATTEMPTS_BEFORE_CANCEL` condition in sync between the two if it changes, since they don't share a component. Customer status lookup is the public `GET /api/storefront/orders/lookup?code=&phone=` (merged into the storefront `/track` page, see **Order/message tracking (Track page) & SMS notifications** below): `orderLookupSchema` requires the code be exactly 8 chars (uppercased) and the phone have ≥9 digits, the server compares phones with spaces/dashes stripped, and a wrong phone returns the **same 404 as an unknown code** — keep codes non-enumerable. The response (`serializePublicOrder`) also includes `customerName`, `address`, `updatedAt`, and per-item `imageUrl` (the product's *current* image, joined at read time — `OrderItem` itself has no image snapshot) — safe to expose since the lookup is already phone-gated before any of it is serialized.
- **Admin dashboard overview:** `GET /api/dashboard/stats` (`server/src/routes/dashboard.ts`, ADMIN-only) returns product/order/low-stock counts; low-stock uses the same `stock > 0 && stock < lowStockThreshold` bounds as the client's `getStockStatus` (out-of-stock is a separate bucket, not counted as low-stock) — keep the two in sync if that logic changes. Rendered as `StatCard`s at the top of `DashboardPage.tsx`, each showing a `Skeleton` while its value is `undefined`; `StatCard` also accepts an optional `suffix` (e.g. `"%"`) and renders `"—"` when the value is `null` (distinct from `undefined`'s loading skeleton) — used by `draftSuccessRate` (Phase 6.8), computed via `prisma.message.groupBy({ by: ["draftStatus"] })` over `AI_DRAFT` messages as (SENT_UNEDITED + SENT_EDITED) / (SENT_UNEDITED + SENT_EDITED + DISCARDED), excluding still-`PENDING` drafts from the denominator (they haven't been judged yet) and reporting `null` rather than `0` when nothing's been reviewed. A second chart (Phase 4.7b) shows daily sold-out product counts: `server/src/lib/product-stock-snapshot-job.ts`'s `takeProductStockSnapshot` runs on a pg-boss cron (`PRODUCT_STOCK_SNAPSHOT_QUEUE`, scheduled just after midnight UTC in `queue.ts`), upserting a `ProductStockSnapshot` row (`date` unique, `soldOutCount`, `soldOutProductIds`) for products with `stock: 0`. `GET /api/dashboard/sold-out-history` returns a 30-day series with `null` (not `0`) for days before the tracking job ever ran, distinct from a confirmed-zero day — same null-vs-zero convention as `draftSuccessRate` — rendered by `SoldOutChart.tsx` (recharts `BarChart`); clicking a bar opens `SoldOutProductsDialog.tsx` (`GET /api/dashboard/sold-out-history/:date`) listing that day's sold-out products linked to their product page. Three further stats live in `server/src/lib/dashboard-metrics.ts` (kept out of the route file, same separation as `product-classification-metrics.ts`), all windowed to the trailing 30 days (7 for orders) rather than all-time: `ordersThisWeek` is a plain rolling-7-day `Order` count; `avgFirstResponseMinutes` averages the gap between `Inquiry.createdAt` and the first message the customer actually saw (`sender: STAFF`, or `AI_DRAFT` with `draftStatus: AUTO_RESOLVED` — a still-`PENDING`/`DISCARDED` draft was never customer-visible), `null` when no inquiry in the window has gotten a reply yet; `draftLittleEditRate` is the share of approved (`SENT_UNEDITED`/`SENT_EDITED`) drafts sent effectively as-written — `SENT_UNEDITED` always counts, `SENT_EDITED` counts too when a word-level Sørensen–Dice similarity between the draft and the sent text is ≥0.85. That comparison needs the sent `STAFF` message's body, which the original `AI_DRAFT` row has no link to by default — `Message.sourceDraftMessageId` (nullable self-FK, `onDelete: SetNull` since it's informational, not integrity-critical) is set only on the `STAFF` message minted by the approve route (`server/src/routes/inquiries.ts`), leaving the draft row itself un-mutated beyond `draftStatus` as before. All three follow the existing `null`-vs-`0` convention (no data yet vs. a confirmed zero/rate).
- **Settings:** store-wide config lives in the `Setting` key-value table (`key String @id`, `value Json`) read via `getSettings()` in `server/src/lib/settings.ts`, which merges rows over `DEFAULT_SETTINGS` from `@es-market/core` — no seed needed for new keys, just add a default. Admin-only `GET`/`PUT /api/settings` + admin UI at `/admin/settings` (`client/src/pages/SettingsPage.tsx`); values safe for customers are also exposed on the public `GET /api/storefront/settings`.
- **Inquiries:** channel-agnostic `channel` field from day one (`InquiryChannel` enum, currently just `WEBSITE` — WhatsApp/Instagram are phase 2, added later as additional enum values via an additive migration, not a breaking one). `Inquiry.status` (`OPEN`/`RESOLVED`/`CLOSED`) follows the `Order` pattern: no `deletedAt`, the entity is never deleted, its lifecycle ends via a terminal status instead. There's no separate `queue` column — the inbox queue view derives "my queue"/"unassigned"/"all" from `assignedAgentId` (+ an optional `status` filter), validated by `inquiryListQuerySchema`'s `queue` param (`"mine"` is always resolved server-side from `req.user.id`, never trusted from the client); assignment itself uses the same optional-single-owner-assignment pattern as `Product.assignedAgentId` (nullable FK + relation + index), except **any staff role can be assigned/claim an inquiry**, not just AGENT like Product. `Message.sender` (`CUSTOMER`/`STAFF`) is an explicit enum rather than inferring the author from `authorUserId`'s nullability, and is the extension point future phases will add to (e.g. an `AI_DRAFT` value). STORED` — every subsequent migration attempt auto-generates spurious `ALTER COLUMN ... DROP DEFAULT` / `DROP INDEX` statements against the `kb_article` search columns, which fails against the shadow DB (`ERROR: column "search_en" ... is a generated column`) and would silently drop the FTS indexes for real if applied as-is. When this happens: review the autogenerated `migration.sql`, delete the spurious `kb_article`-related statements (keep only the statements for what you actually changed), apply the corrected SQL directly via `psql` against the real dev DB, then run `bunx prisma migrate resolve --applied <migration_name>` to mark it applied without re-running the shadow-DB diff. Seen first in migration `20260721190731_inquiry_ai_classification`. **This compounds on every subsequent migration** — since the previous migration's `migration.sql` was hand-edited after Prisma recorded its checksum, `prisma migrate dev`'s shadow-DB replay eventually fails hard enough to propose `prisma migrate reset` (**never run this** — it drops the entire dev database). When `migrate dev`/`--create-only` won't cooperate at all: skip it entirely — hand-write the migration directory (`mkdir prisma/migrations/<timestamp>_<name>`, matching Prisma's own SQL syntax/style) and its `migration.sql` from scratch based on the actual schema.prisma diff, apply it directly via `psql`, then `prisma migrate resolve --applied <name>`. A "Dismiss" button (shown once a suggestion is loaded) calls `classifyMutation.reset()` — purely client-side, since this flow's suggestion is never persisted server-side, unlike the bulk flow below. Accepting either field pings `POST /api/ai/classify-product/accept` (`pingClassificationAccepted`, fire-and-forget) which feeds a singleton `ProductClassificationMetric` row (`categorySuggested`/`categoryAccepted`/`tagsSuggested`/`tagsAccepted`), surfaced on the dashboard as an acceptance-rate stat. `recordAcceptance` (`server/src/lib/product-classification-metrics.ts`) uses a guarded raw `UPDATE ... WHERE "categoryAccepted" < "categorySuggested"` (a column-vs-column comparison Prisma's `updateMany` filters can't express, same class of escape hatch as `kb-search.ts`'s raw tsvector queries) rather than an unconditional `upsert`, so a stray/duplicate accept ping can never push the counter past its own denominator or create a row with no prior suggestion.
  - **Bulk reclassify-all** (`ProductsTable.tsx`'s `SuggestionBadge`, `client/src/pages/ProductsPage.tsx`'s "Reclassify all" button): `POST /api/products/reclassify-all` enqueues one `classify-product` pg-boss job per non-deleted product (`localConcurrency: 2`, `product-classification-job.ts`), each writing its result onto the product row itself (`aiSuggestedCategoryId`/`aiSuggestedTags`/`aiSuggestedAt`) rather than returning it synchronously; `GET /api/products/reclassify-status?since=` approximates batch progress by counting products whose suggestion was recomputed since a timestamp (**not** scoped to one specific batch — two overlapping batches would double-count, an accepted v1 simplification). Overlapping batches are prevented at the source instead: `acquireReclassifyLock()` (`server/src/lib/product-reclassify-lock.ts`) is a singleton `ProductReclassifyBatch` row acquired via a guarded `INSERT ... ON CONFLICT ("id") DO UPDATE ... WHERE "expiresAt" < now()`, TTL-based (30 min) rather than completion-triggered — self-healing if a batch crashes, at the cost of blocking a legitimately-finished batch from an immediate re-run until the TTL lapses. **pg-boss's own `boss.getQueue(name).queuedCount`/`activeCount` were tried first and rejected** — confirmed live that they lag several seconds behind real enqueues (maintained by a periodic background job, not updated synchronously on `send()`), too slow to catch a rapid double-click. `SuggestionBadge` offers Apply (merges the suggestion into the product via the normal `PUT` route, which also clears the `aiSuggested*` fields) and Dismiss (`POST /products/:id/dismiss-suggestion`) — Dismiss is a guarded `updateMany` on `aiSuggestedAt` matching the timestamp the client last saw (an optimistic-concurrency token, `dismissProductSuggestionSchema` in `core/src/schemas/product-classification.ts`), so a suggestion recomputed by a concurrent bulk run in between isn't silently discarded by a stale click; a 409 just triggers a client refetch, no error toast.
- **Product tags & storefront filtering (Phase 7.3):** `Product.tags` is a plain `String[]` (no index — every tag query is a full non-deleted-product scan, an accepted v1 simplification at this catalog's scale). `tagSchema` (`core/src/schemas/product.ts`) trims, caps at 50 chars, and lowercases every tag on write (`createProductSchema`/`updateProductSchema`) so `"Rice"`/`"rice"` don't fragment into near-duplicate tags; the storefront's `tag` query param (`storefrontProductListQuerySchema`) is lowercased the same way, so a differently-cased tag (e.g. a hand-typed URL) still matches the stored lowercase value via the exact-match `tags: { has: tag }` filter in `GET /api/storefront/products`. `GET /api/storefront/tags` returns the distinct sorted tag list for the filter dropdown, flattened/deduped in JS (same "fine at this scale" tradeoff as the AI-classification catalog prompt above). Tag chips are clickable in two places: `client/src/pages/storefront/ProductsPage.tsx`'s product-card badges call `setTag(tag)` directly (same page, no navigation), while `ProductDetailPage.tsx`'s tags are `Link`s to `/products?tag=<tag>` — the products page reads that param once at mount (`useSearchParams`, read-only — not synced back to the URL on further filter changes) to hydrate its filter state so the link actually lands pre-filtered.

Define each schema once in the `core` package (`core/src/schemas/`, exported from `core/src/index.ts` along with its inferred type) and import it from `@es-market/core` in both client and server — never duplicate a schema in `client/` or `server/`. Server routes validate request bodies with the shared schema + `safeParse` (400 with the first issue's message on failure; see `server/src/routes/users.ts`); the client uses the same schema in forms (see the Forms bullet), which keeps error messages identical on both sides. Example: `createUserSchema` in `core/src/schemas/user.ts`. Every free-text string field gets an explicit `.max(...)`, not just a `.min(...)` — e.g. `localizedNameSchema` (`core/src/schemas/localized.ts`, shared by `Product.name`/`Category.name`) caps each language at 200 chars, `localizedDescriptionSchema` at 1000; ID-shaped fields like `categoryId`/`assignedAgentId` in `createProductSchema` also get a generous bound (100) even though they're not user-composed prose, since nothing upstream otherwise limits their length.

Reference implementation: the create-user form in `client/src/pages/CreateUserDialog.tsx` (schema-driven validation, inline `text-destructive` field errors, submit wired to a TanStack `useMutation`). - **Soft delete:** entities that may be referenced elsewhere later (e.g. a future Order referencing Product) are soft-deleted via a nullable `deletedAt DateTime?` column, not hard `DELETE`s — see `User` and `Product` in `schema.prisma`. List queries filter `where: { deletedAt: null }`; the `DELETE` route sets `deletedAt: new Date()` and 404s if the row is already deleted. Only hard-delete an entity if nothing will ever need to reference the deleted row again. This check belongs on every route that reads a specific row by id, not just `DELETE` — `PUT /api/users/:id` originally fetched its target without checking `deletedAt`, silently allowing a deactivated user's name/email/password to be edited (harmless in that they still can't log in, since `auth.ts` blocks session creation for a soft-deleted user, but inconsistent with the delete/reactivate lifecycle); fixed to 404 the same as every other soft-delete-aware route.
- **Pricing:** `Product.price` is a whole-number `Int` (no decimal/cents subunits) — matches how `stock`/`lowStockThreshold` are already modeled and avoids float-precision issues. Don't introduce cents-based conversion without an explicit decision to do so.
- **List ordering:** list queries order by `createdAt: "desc"` (newest first) unless a feature has a specific reason to differ — see `GET /api/products` in `server/src/routes/products.ts`.
- **Optional single-owner assignment:** an entity assignable to one staff member (e.g. `Product.assignedAgentId`) is a nullable FK on the owned entity — not a join table — mirroring the existing required `categoryId` FK pattern. Reference implementation: `Product.assignedAgentId`/`assignedAgent` in `schema.prisma`, validated in `POST`/`PUT /api/products` the same way `categoryId` is (fetch the target user, 404 `"Agent not found"` if missing, soft-deleted, **or not the expected `Role`** — don't just check existence). The include/select shape stays minimal (`{ id, name }`), not the full user row. On the client, the assignee `Select` (`ProductForm.tsx`) is populated from `GET /api/users` filtered client-side to the target role, with an explicit "Unassigned" option; since shadcn's `Select` can't use a literal empty-string value, the "Unassigned" choice maps to `""` in the form and the shared zod schema preprocesses `"" → undefined` (see `assignedAgentId` in `core/src/schemas/product.ts`) so omitting the field un-assigns rather than validation-failing. The entity's list table gets a corresponding non-sortable column rendering the assignee's name or "Unassigned".
- **File uploads:** Cloudinary cloud object storage (`server/src/lib/cloudinary.ts`) — a migration off the original local-disk v1 approach, per `tech-stack.md`. `cloudinary.config()` reads `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` via `requiredEnv` (same fail-fast-at-startup posture as `OPENAI_API_KEY`) — Cloudinary is the sole storage backend for product images, category cover images, and customer avatars, all catalog/profile assets served publicly and unauthenticated. Upload is a **separate endpoint** taking `multipart/form-data`, not folded into the entity's JSON create/edit routes — this keeps those routes' zod schemas and request contracts untouched. `multer`'s `fileFilter` (declared-mimetype allowlist, cheap early rejection) + `limits.fileSize` enforce a first pass server-side; wrap the `multer` middleware to translate `MulterError` into the same `400 { error: message }` shape other routes use. **The declared mimetype/filename extension is never trusted as the real gate** — a multipart `Content-Type` field is attacker-controlled, so `multer.memoryStorage()` buffers the upload instead of streaming it straight to Cloudinary, then each route runs the buffer through `file-type`'s `fileTypeFromBuffer` (magic-byte detection) and only calls `uploadImageBuffer` — under a server-generated `randomUUID()` `public_id`, never the client's filename — once every file in a batch genuinely matches an allowed image type (product images stay all-or-nothing: one bad file in a multi-file upload rejects the whole batch rather than silently dropping it); otherwise it 400s with the same message the mimetype-level filter uses. `uploadImageBuffer(buffer, folder, publicId)` (`cloudinary.uploader.upload_stream`, `resource_type: "image"`) returns the Cloudinary `secure_url`, stored as-is in the DB (`Product.images`, `Category.imageUrl`, `Customer.image`) — the same role the old `/api/uploads/...` local path played, so no schema changes were needed for this migration. Deletion (a replaced avatar/cover image, or a removed product image) resolves the stored URL's filename back to a `folder/<uuid>` public_id via `publicIdFromImageUrl` and calls `deleteCloudinaryImage` (`cloudinary.uploader.destroy`, best-effort — `.catch(() => {})`, same posture as the old `unlink().catch(() => {})`). No local `server/uploads/` directory or `express.static` mount exists anymore.
- **Product images (multiple):** `Product.images String[] @default([])` — an ordered list of Cloudinary `secure_url`s (see the File uploads convention bullet above), first is the primary/thumbnail shown in list/card views; plain array rather than a relation table, same "fine at this catalog's scale" precedent as `tags`/`aiSuggestedTags`, capped at `MAX_PRODUCT_IMAGES = 8` (`core/src/schemas/product.ts`, shared by client UI disabling and server enforcement). `POST /api/products/:id/images` (multipart field `"images"`, admin-only) **appends** validated images to the existing array rather than replacing it, 400ing with `"A product can have at most 8 images"` if the total would exceed the cap. `DELETE /api/products/:id/images/:filename` removes one image by filename (matched against the stored URL's basename, resolved to a Cloudinary public_id) — a guarded fetch-then-update rather than a race-safe `updateMany` (acceptable here: single admin editing their own product, low concurrency, worst case is a recoverable stale write), deletes the Cloudinary asset best-effort, 404s if that filename isn't currently on the product. - **Product variants (related products):** `Product.variantGroupId String?` (`@@index`ed) — a plain, server-generated (`randomUUID()`) shared token linking products that are "the same item, different variant" (e.g. color); never client-supplied, and inherently symmetric (a shared group token, not a directional relation), so no bidirectional-sync bookkeeping is needed like `relatedProductIds`-style arrays would require. `POST /api/products/:id/variants` (body `{ productId }`, admin-only) links another product in — generates a group id on the current product if it doesn't have one yet, 409s if the target already belongs to a *different* group (no silent merging), idempotent no-op if already linked. `DELETE /api/products/:id/variants/:variantProductId` unlinks one; if the group would then have ≤1 member left, that lone member's `variantGroupId` is cleared too (a "group of one" is meaningless). `GET /api/products/:id` (admin) and `GET /storefront/products/:id` (public) each resolve siblings via a second query only on the single-product routes — the paginated list routes don't pay this cost. The public route never exposes the raw `variantGroupId` itself, only the resolved `relatedProducts` array (empty when ungrouped, not a schema branch the client needs to special-case). Client: `ProductVariantLinks.tsx` (inside `EditProductDialog.tsx`, edit-only — linking needs two already-saved products) self-fetches `GET /api/products/:id` fresh via `useQuery(["products", id])` rather than trusting a possibly-stale table-row snapshot (the same staleness class of bug fixed for the image gallery), with a debounced search box (reusing `GET /api/products?search=`) to find candidates to link. Validated in `createProductSchema`/`updateProductSchema` (`core/src/schemas/product.ts`) with the same empty-string-to-undefined preprocessing as `assignedAgentId`. **No two members of one variant group may share the same (size, color) pair** — a silent duplicate would give the storefront picker two buttons for the same option, navigating unpredictably to whichever a query happens to return first. Enforced (409 "A variant with that size and color is already in this group") in two places in `server/src/routes/products.ts`: `POST /products/:id/variants` (checked against every existing member of the target's group, or just the target itself if it isn't grouped yet — before the group-merge write) and `PUT /products/:id` (checked against the product's current siblings whenever it's already grouped and the edit sets a non-null size or color) — editing an already-linked variant's label into collision with a sibling is just as real a path to the bug as linking a duplicate in.
