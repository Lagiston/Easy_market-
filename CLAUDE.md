# ES-Market

AI-powered e-commerce site + internal dashboard for a physical store. Customers browse and order online (pay on delivery/pickup); staff manage the catalog, orders, and an AI-assisted support inbox where every AI-drafted reply is reviewed by an agent before sending.

## Key documents

- [Project-Scope.md](Project-Scope.md) — problem, features, scope decisions, resolved open questions
- [tech-stack.md](tech-stack.md) — stack choices and rationale
- [implementation-plan.md](implementation-plan.md) — phased task breakdown; keep checkboxes updated as tasks complete

## Stack

Bun workspaces monorepo: `client/` (Vite + React + TypeScript), `server/` (Express 5 + TypeScript, runs natively on Bun — no build step), and `core/` (`@es-market/core` — shared TypeScript consumed as source by both, no build step; holds the zod schemas). PostgreSQL via Prisma. Vercel AI SDK (OpenAI provider) for AI features (server-side only, never from the browser). Client UI: Tailwind CSS v4 + shadcn/ui.

## Commands

```sh
bun install              # install all workspace deps (from root)
bun run dev:server       # Express on Bun with --hot, http://localhost:3000
bun run dev:client       # Vite dev server, http://localhost:5173 (proxies /api to :3000)
bun run --cwd server typecheck   # tsc --noEmit
bun run test:e2e         # Playwright E2E: sets up the test DB, then runs specs in e2e/
bun run --cwd client test        # Vitest component tests, single run
bun run --cwd client test:watch  # Vitest component tests, watch mode
```

## Component testing

Component tests use Vitest + React Testing Library, colocated with the component as `*.test.tsx` (e.g. `client/src/pages/UsersPage.tsx` → `client/src/pages/UsersPage.test.tsx`). Config lives in `client/vitest.config.ts` (jsdom environment, `@` alias matching Vite's, setup file at `client/src/test/setup.ts` which loads `@testing-library/jest-dom`).

- Mock `axios` with `vi.mock("axios")` / `vi.mocked(axios, { deep: true })` rather than hitting the network — reset mocks in `beforeEach`.
- Any component using TanStack Query must be rendered through `renderWithQuery` from `client/src/test/render-with-query.tsx` (wraps in a fresh `QueryClientProvider` with retries disabled), not `render` directly.
- Prefer `screen.findBy*` / `waitFor` for async states (loading → success/error) over arbitrary waits.
- For long strings (e.g. testing a `.max()` validation bound past a few hundred characters), use `fireEvent.change` instead of `userEvent.type` — typing key-by-key over 1000+ characters is slow enough to flake against the test timeout under parallel load; `fireEvent.change` sets the value in one go and still exercises the same submit-time validation.
- Run `bun run --cwd client test` after writing or changing component tests, and `bun run --cwd client test:watch` while iterating.

This is separate from Playwright E2E (below) — component tests exercise one component in isolation with mocked I/O; E2E drives the real app end-to-end.

**Component tests are the default for new coverage.** Form validation, dialog open/close and confirm/cancel behavior, loading/error/success states, and request payloads built from mocked axios calls all belong here, not in E2E — they don't need a real server, DB, or filesystem to exercise.

## E2E testing

Playwright E2E tests live in `e2e/` and run against a separate test database (`es_market_test`, never the dev DB).

**Depend on component tests; only run/add E2E tests when absolutely necessary** — reserve it for what actually requires the real stack: real server persistence (a row surviving reload), real filesystem/multer behavior (file-type or size rejection, actual upload/serving), and real auth/session-based routing (role redirects, unauthenticated redirects). If a behavior can be verified by mocking the HTTP layer in a component test, put it there instead and keep the E2E spec to one or two happy-path/integration cases per flow.

**Always delegate writing, extending, or fixing E2E tests to the `e2e-test-writer` subagent** (`.claude/agents/e2e-test-writer.md`) — launch it via the Agent tool rather than editing specs directly in the main conversation. It carries the full setup details (test env, ports, DB lifecycle, auth constraints) and the project's test conventions (locator style, parallel-safety, assertion standards), and it runs the specs it writes. Give it the feature or flow to cover and any acceptance criteria; it handles the rest.

## Authentication

Better Auth (email/password) with the Prisma adapter on PostgreSQL — DB-backed sessions with an opaque cookie ID (no JWT). This section covers the **staff** instance: public signup is disabled (`disableSignUp: true`); the admin is seeded and creates other accounts. See **Customer accounts** below for the separate, second Better Auth instance customers use.

- **Server config:** `server/src/lib/auth.ts`. The handler is mounted in `server/src/index.ts` at `app.all("/api/auth/*splat", toNodeHandler(auth))` — this must stay **before** `express.json()`, or Better Auth requests will hang on the consumed body.
- **Roles:** `role` is a Better Auth additional field on `user` (default `Role.AGENT`, `input: false` so clients can't set it); the Prisma `Role` enum is `ADMIN | AGENT`. See the Role enum bullet under Conventions & decisions — never compare against the raw `"ADMIN"`/`"AGENT"` strings.
- **Route protection:** `server/src/middleware/require-auth.ts` exports `requireAuth` (401s if no session, then populates `req.user`/`req.session`) and `requireRole(...roles)` (403s otherwise). Example: `app.get("/api/me", requireAuth, ...)`.
- **Client:** `client/src/lib/auth-client.ts` creates `authClient` from `better-auth/react`, with `inferAdditionalFields` so `role` is typed on the session user (exported as `SessionUser`). Same-origin: Vite proxies `/api` to :3000, so no `baseURL` is set. Use `authClient.useSession()` for auth state, `authClient.signIn.email()` / `authClient.signOut()` for flows; `ProtectedRoute` redirects unauthenticated users to `/admin/login` and takes an optional `roles` prop for role-gated routes (e.g. `<ProtectedRoute roles={[Role.ADMIN]} />` wraps `/admin/users`; disallowed roles are redirected to `/admin`). All staff-facing routes live under `/admin` (see `App.tsx`); `/` is the public storefront. Role-only UI (like the "Users" nav link in `Layout`) checks `user.role === Role.ADMIN`. Client gating is UX only — protect the matching API routes with `requireRole` too.
- **Admin seeding:** `bun run --cwd server seed` (also wired as the Prisma seed) — idempotent, reads `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_NAME`, hashes with `better-auth/crypto` under the `credential` provider. Rejects passwords under 12 chars or the `change-me` placeholder.
- **Env vars** (`server/.env`, see `.env.example`): `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (:3000), `CLIENT_URL` (:5173, listed in `trustedOrigins`), plus the `ADMIN_*` seed vars. `auth.ts` **throws at startup** if `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, or `CLIENT_URL` is missing (no silent fallbacks); `useSecureCookies` is forced on when `NODE_ENV=production`.
- **Rate limiting:** `server/src/middleware/rate-limit.ts` (`express-rate-limit`) — mounted in `index.ts` only when `NODE_ENV=production`: `/api/auth` and `/api/customer-auth` each get 20 req/IP/15 min (brute-force/signup-spam, same `authLimiter`), `/api/storefront/orders` 10 (order spam), `/api/customer/orders/link-by-phone` 10 (`linkOrdersLimiter` — each request is a phone-number guess that, if it hits, permanently transfers a stranger's order to the requester's account; `requireCustomerAuth` alone doesn't stop one account from iterating many numbers), the rest of `/api` 300. Dev and E2E runs are unthrottled. If prod sits behind a proxy, `app.set("trust proxy", ...)` still needs to be configured.
- **Security headers:** `helmet()` is mounted as the very first middleware in `server/src/index.ts` (before rate limiters and the Better Auth handlers), using its defaults unmodified — this is an API-only server with no HTML views, so the default CSP/HSTS/frame-ancestors/nosniff set is safe as-is with nothing to tune.

## Customer accounts

A second, fully separate Better Auth instance from the staff one above — not a third `Role` value on the staff `User` table. The staff instance has public signup deliberately disabled and `role` is a staff-only concept (`ADMIN | AGENT`, exhaustively checked throughout `requireRole`/agent-assignment dropdowns/etc.); reusing it for customers would mean either weakening that signup gate or bolting an unrelated concept onto every place that treats `Role` as exhaustive. Building phase-2 of the guest-checkout decision in `Project-Scope.md` ("guest checkout for v1 — customer accounts are a phase 2 candidate"), scoped to what that doc flagged as the actual point of accounts: order history, not just a login.

- **Server config:** `server/src/lib/customer-auth.ts` — `emailAndPassword: { enabled: true }` with signup left on (the opposite of the staff instance), pointed at its own `Customer`/`CustomerSession`/`CustomerAccount`/`CustomerVerification` Prisma models via `modelName`, mounted at `basePath: "/api/customer-auth"` with `advanced.cookiePrefix: "es-market-customer"` so its routes/cookies never collide with the staff instance's `/api/auth`/`better-auth.*`. **Gotcha found live:** Better Auth's internal FK field name back to the user is always `userId` regardless of what the user model is called — since these Prisma models name that column `customerId` (matching this feature's own naming), `session`/`account` both need an explicit `fields: { userId: "customerId" }` override or every write 500s with a confusing "Argument `customer` is missing" Prisma error. The handler is mounted the same way as the staff one, `app.all("/api/customer-auth/*splat", toNodeHandler(customerAuth))`, also **before** `express.json()`.
- **No email flows:** no email-sending infrastructure exists anywhere in this repo. `requireEmailVerification` is left at its default `false` (signup works immediately, no verification step — Better Auth's default, confirmed via docs), and there's no self-service password reset. A customer who forgets their password has no recovery path — a known v1 gap, not solved.
- **`Customer` has no `deletedAt`:** unlike `User`/`Product`, there's no account-deactivation flow being built, so a soft-delete column would be speculative — add it if/when that flow exists.
- **Route protection:** `server/src/middleware/require-customer-auth.ts` exports `requireCustomerAuth`, mirroring `requireAuth` exactly but populating `req.customer`/`req.customerSession` from `customerAuth.api.getSession`.
- **Client:** `client/src/lib/customer-auth-client.ts` creates `customerAuthClient` (`createAuthClient({ basePath: "/api/customer-auth" })`, exported session-user type `CustomerSessionUser`). `CustomerProtectedRoute` (mirrors `ProtectedRoute` but redirects to `/account/login` instead of `/admin/login`, and renders no chrome of its own — it nests *inside* `StorefrontLayout`'s routes rather than wrapping a separate layout, since account pages want the normal storefront header/footer) wraps `/account` and `/account/orders` in `App.tsx`; `/account/login` and `/account/signup` are public storefront routes. `StorefrontLayout.tsx`'s header shows a "Sign in" link (→ `/account/login`) or the customer's name (→ `/account`) based on `customerAuthClient.useSession()`.
- **Order linking is soft/optional auth** — a pattern used nowhere else in this codebase (everything else is a hard `requireAuth`/`requireRole` gate). `POST /api/storefront/orders` stays public/unauthenticated either way; it just additionally calls `customerAuth.api.getSession(...)` inline and attaches `customerId` (nullable FK on `Order`, `@@index`ed) when a valid customer session cookie happens to be present, guest orders unaffected. `customerName`/`customerPhone`/`address` stay point-in-time snapshots regardless (same precedent as `OrderItem.productName`/`unitPrice`), so `customerId` is purely an additional identity link, not a replacement.
- **`GET /api/customer/orders`** (`server/src/routes/customer.ts`, `requireCustomerAuth`) — the signed-in "My orders" list, filtered to `customerId: req.customer.id`. Shares a `serializePublicOrder`/`orderWithItems` helper (exported from `server/src/routes/orders.ts`) with the guest `GET /storefront/orders/lookup` route, since both return the identical customer-safe order shape (no `customerName`/`customerPhone`/`address`/`customerId` — that's `serializeOrder`, the separate staff-only version in the same file).
- **Claiming past guest orders**: `POST /api/customer/orders/link-by-phone` (`requireCustomerAuth`) lets a signed-in customer voluntarily link guest orders placed before they had an account — **never automatic/silent**, since a phone number isn't verified proof of ownership; the customer has to explicitly submit the phone they ordered with (`AccountOrdersPage.tsx`'s "Ordered as a guest before?" form). Matches `customerPhone` normalized the same way as the guest lookup route (reuses `normalizePhone`, exported from `orders.ts`) over all still-`customerId: null` orders — v1 simplification, matched in JS rather than a normalized SQL comparison (same "fine at this store's scale" tradeoff already accepted for the tag-flattening and AI-classification-catalog queries elsewhere). The final `updateMany`'s `where` re-checks `customerId: null`, so it can only ever claim still-unclaimed orders — one customer can't steal an order another account already linked, even if they know the same phone number. Rate-limited in production (see the Rate limiting bullet above) since a signed-in account could otherwise iterate phone numbers to permanently hijack strangers' orders. Returns `{ linkedCount }`; the client shows a pluralized "Linked N orders" message and refetches `/api/customer/orders` only when `linkedCount > 0`.
- **Explicitly out of scope for this pass:** cart (confirmed client-only/localStorage, no server sync anywhere), inquiries/chat (their own independent guest-identity mechanism via `inquiry-session.ts`, untouched), and checkout-form prefill from the account profile.

## Conventions & decisions

- **Auth:** DB-backed sessions (Prisma `Session` model, opaque cookie ID) — no JWT, no in-memory sessions. Staff accounts only (ADMIN/AGENT roles), no public signup; admin is seeded. See the Authentication section above for implementation details.
- **Prisma enums:** never compare or assign enum values as raw string literals (`"ADMIN"`, `"DELIVERY"`, …). Server-side Prisma code (routes, `requireRole`, seeds) uses the Prisma-generated enums (`../generated/prisma/client`), which are the source of truth for the DB columns. Everywhere else — client code, shared types, test fixtures — import the mirror const object from `@es-market/core` (the client has no access to the Prisma-generated ones): `Role` in `core/src/schemas/user.ts`, `FulfillmentType` in `core/src/schemas/order.ts`. New Prisma enums that cross the API boundary get the same mirror-const treatment.
- **Languages:** English is primary/required; Arabic, Swahili, French optional with English fallback. Arabic needs RTL. Launch content is entered in English + Arabic only.
- **Cart:** client-side only — `CartProvider`/`useCart` in `client/src/lib/cart.tsx`, persisted to localStorage (`es-market-cart`), no server cart. Items are display snapshots of the product (localized name, price, imageUrl, stock) with quantities clamped to stock; the order API revalidates price and stock server-side, so never trust cart values for money or availability. `clampQuantity` treats zero stock as a special case (returns `0`, not `1`) — `addItem`/`updateQuantity` remove the item outright when this happens rather than storing a zero-quantity entry, since a stray zero-quantity item would violate the same `quantity > 0` invariant `loadCart` already enforces when validating a persisted cart from `localStorage`.
- **Checkout:** guest only, no customer accounts in v1. Staff phone-call confirmation (no SMS OTP). Self-delivery, city-only, flat fee with a free-delivery threshold — both are `Setting` rows (see Settings bullet), and `computeDeliveryFee` in `server/src/lib/settings.ts` is the single place that fee logic lives (pickup is always free). The checkout form is `client/src/pages/storefront/CheckoutPage.tsx` (`checkoutFormSchema` = the customer fields; `placeOrderSchema` adds `items`, which the client fills from the cart); the confirmation page reads the placed order from router `location.state` and redirects home if absent.
- **Orders:** non-sequential random order codes for customer status lookup (code + phone) — generated by `server/src/lib/order-code.ts` (8 chars, ambiguous characters excluded), unique column, retry the whole transaction on a P2002 collision (a failed insert aborts the Postgres transaction, so don't retry inside it). `POST /api/storefront/orders` (`server/src/routes/orders.ts`) prices everything from DB rows (never client input), then in a `prisma.$transaction` does a guarded decrement per item (`updateMany` with `stock: { gte: quantity }`, 409 naming the product when `count !== 1` — race-safe stock validation + decrement in one statement) and creates the order with `OrderItem` rows snapshotting `productName`/`unitPrice` (products are editable and soft-deletable; history must show what was charged). Order subtotal/total are **not stored** — derive them from items + `deliveryFee`. Orders are never deleted (no `deletedAt`); they end via `status: CANCELLED`. `Order.customerId` (nullable) links to a signed-in customer's account when present — see **Customer accounts** below for how/when it's set. Staff order endpoints (`GET /api/orders`, `POST /api/orders/:id/{call-attempt,confirm,cancel}`) use `requireAuth` only — order handling is ADMIN **and** AGENT work, unlike the ADMIN-only catalog/user routes; status transitions are race-safe guarded `updateMany`s on the expected current status (`count === 0` → 404 if the order doesn't exist, else 409), and cancel (allowed from RECEIVED/CONFIRMED, zod-validated `CancelReason`) restores stock in the same transaction by incrementing each item's quantity. Phone confirmation: staff log failed calls (`callAttempts`); at `CALL_ATTEMPTS_BEFORE_CANCEL` (3, in `@es-market/core`) the UI offers cancel-as-unreachable (a guided `CancelUnreachableOrderDialog` pre-filling `CUSTOMER_UNREACHABLE`) — on both the order list (`OrdersTable.tsx`) and the order detail page (`OrderDetailPage.tsx`); keep the `callAttempts >= CALL_ATTEMPTS_BEFORE_CANCEL` condition in sync between the two if it changes, since they don't share a component. Customer status lookup is the public `GET /api/storefront/orders/lookup?code=&phone=` (storefront page `/order-status`): `orderLookupSchema` uppercases the code, the server compares phones with spaces/dashes stripped, and a wrong phone returns the **same 404 as an unknown code** — keep codes non-enumerable; the response is the public order shape only (status, item snapshots, derived totals — no customer fields).
- **Admin dashboard overview:** `GET /api/dashboard/stats` (`server/src/routes/dashboard.ts`, ADMIN-only) returns product/order/low-stock counts; low-stock uses the same `stock > 0 && stock < lowStockThreshold` bounds as the client's `getStockStatus` (out-of-stock is a separate bucket, not counted as low-stock) — keep the two in sync if that logic changes. Rendered as `StatCard`s at the top of `DashboardPage.tsx`, each showing a `Skeleton` while its value is `undefined`; `StatCard` also accepts an optional `suffix` (e.g. `"%"`) and renders `"—"` when the value is `null` (distinct from `undefined`'s loading skeleton) — used by `draftSuccessRate` (Phase 6.8), computed via `prisma.message.groupBy({ by: ["draftStatus"] })` over `AI_DRAFT` messages as (SENT_UNEDITED + SENT_EDITED) / (SENT_UNEDITED + SENT_EDITED + DISCARDED), excluding still-`PENDING` drafts from the denominator (they haven't been judged yet) and reporting `null` rather than `0` when nothing's been reviewed. A second chart (Phase 4.7b) shows daily sold-out product counts: `server/src/lib/product-stock-snapshot-job.ts`'s `takeProductStockSnapshot` runs on a pg-boss cron (`PRODUCT_STOCK_SNAPSHOT_QUEUE`, scheduled just after midnight UTC in `queue.ts`), upserting a `ProductStockSnapshot` row (`date` unique, `soldOutCount`, `soldOutProductIds`) for products with `stock: 0`. `GET /api/dashboard/sold-out-history` returns a 30-day series with `null` (not `0`) for days before the tracking job ever ran, distinct from a confirmed-zero day — same null-vs-zero convention as `draftSuccessRate` — rendered by `SoldOutChart.tsx` (recharts `BarChart`); clicking a bar opens `SoldOutProductsDialog.tsx` (`GET /api/dashboard/sold-out-history/:date`) listing that day's sold-out products linked to their product page.
- **Settings:** store-wide config lives in the `Setting` key-value table (`key String @id`, `value Json`) read via `getSettings()` in `server/src/lib/settings.ts`, which merges rows over `DEFAULT_SETTINGS` from `@es-market/core` — no seed needed for new keys, just add a default. Admin-only `GET`/`PUT /api/settings` + admin UI at `/admin/settings` (`client/src/pages/SettingsPage.tsx`); values safe for customers are also exposed on the public `GET /api/storefront/settings`.
- **Inquiries:** channel-agnostic `channel` field from day one (`InquiryChannel` enum, currently just `WEBSITE` — WhatsApp/Instagram are phase 2, added later as additional enum values via an additive migration, not a breaking one). `Inquiry.status` (`OPEN`/`RESOLVED`/`CLOSED`) follows the `Order` pattern: no `deletedAt`, the entity is never deleted, its lifecycle ends via a terminal status instead. There's no separate `queue` column — the inbox queue view derives "my queue"/"unassigned"/"all" from `assignedAgentId` (+ an optional `status` filter), validated by `inquiryListQuerySchema`'s `queue` param (`"mine"` is always resolved server-side from `req.user.id`, never trusted from the client); assignment itself uses the same optional-single-owner-assignment pattern as `Product.assignedAgentId` (nullable FK + relation + index), except **any staff role can be assigned/claim an inquiry**, not just AGENT like Product. `Message.sender` (`CUSTOMER`/`STAFF`) is an explicit enum rather than inferring the author from `authorUserId`'s nullability, and is the extension point future phases will add to (e.g. an `AI_DRAFT` value). Messages are immutable (no `updatedAt`) and cascade-delete with their `Inquiry`. `Inquiry.language` is a plain `String` column (not a Prisma enum — validated against the `LANGUAGES` constant from `core/src/schemas/localized.ts`, same as how `LocalizedName` treats language as plain string keys), captured invisibly from `i18n.resolvedLanguage` when a customer submits (never a visible form field) and surfaced on the staff detail view as a label plus a `dir`/`lang`-aware reply textarea (RTL for Arabic) — a manual affordance only, no translation service. `Inquiry.escalatedAt` is a nullable timestamp **orthogonal to `status`** (not a 4th status value) — an inquiry can be OPEN/RESOLVED and escalated at the same time; escalating reassigns to a specific ADMIN-role user (the one restriction that *is* role-specific) and has no de-escalate action yet.
  - **AI classification (6.4, shipped)**: four nullable fields on `Inquiry` — `aiTopic`/`aiUrgency` (plain strings, `aiUrgency` validated against `INQUIRY_URGENCIES = ["low","medium","high"]` from `core/src/schemas/inquiry-classification.ts`, not a Prisma enum, following the `language` precedent), `aiConfidence` (`Float?`), and `aiProductId` (nullable FK to `Product`, `@relation("InquiryConcernedProduct")`, mirroring `assignedAgentId`). No queue column exists — "auto-routing to queues" means `server/src/lib/inquiry-classification.ts`'s `classifyInquiry(inquiryId, message)` sets `assignedAgentId` itself to the concerned product's `assignedAgent` (only trusting a `productId` the model returns if it's actually in the non-deleted product catalog sent in the prompt — never trusting a raw model-emitted id), reusing the existing mine/unassigned/all derivation as-is. Runs **fire-and-forget** from `POST /storefront/inquiries` (`void classifyInquiry(...).catch(...)`, not awaited) so a slow/failed OpenAI call never affects the guest's `201` response; `classifyInquiry` itself catches `AiIntegrationError` internally and just logs, leaving the inquiry's AI fields `null` on failure — never a guest-visible failure or a crash. v1 sends the *entire* non-deleted product catalog (id + English name) in every classification prompt — fine at expected scale, would need trimming/retrieval (mirroring the KB's FTS approach) if the catalog grows much larger; not solved, flagged. No re-classification on guest follow-up messages — creation-time only.
  - **AI escalation rules (6.5, shipped)**: folded into the same 6.4 classification call rather than a second LLM call — `inquiryClassificationSchema` (`core/src/schemas/inquiry-classification.ts`) has a model-emitted `escalate: boolean` field (the prompt asks the model to judge complaint/refund intent or an explicit human request directly, since string-matching a freeform `topic` after the fact can't reliably catch "I want my money back" as a refund complaint). `classifyInquiry` backstops this deterministically: `LOW_CONFIDENCE_THRESHOLD = 0.5` forces escalation regardless of what the model decided, since a low-confidence call's own judgment about needing a human can't be trusted either. When triggered, sets `escalatedAt: new Date()` — reusing the exact field the manual staff escalate flow uses, but (unlike that flow) **never touches `assignedAgentId`**, since there's no specific admin to hand off to; the inquiry just stays in the unassigned pool for any agent to claim. No new client code needed: `InquiriesTable.tsx`'s escalated icon and `InquiryDetailPage.tsx`'s "Escalated" badge (built in Phase 5) already render for any `escalatedAt !== null`, regardless of who/what set it. "No draft" is a contract for 6.6 (not built yet) to honor — reply-drafting must skip generating a draft whenever `escalatedAt` is non-null; there's no drafting code yet to enforce this against.
  - **AI reply drafting (6.6, shipped)**: `MessageSender` gained its long-anticipated `AI_DRAFT` value (additive enum migration `20260721202737_message_ai_draft`); `Message.sourceKbArticleIds String[] @default([])` records which KB articles informed a draft — a plain string list, not a relation, mirroring `OrderItem`'s `productName` snapshot (historical context for 6.7's future "view draft with sources" UI, not something needing referential integrity against articles that may later change). `server/src/lib/inquiry-draft.ts`'s `draftInquiryReply(inquiryId, message, language)` calls `searchKbArticles` (6.2) for candidates in the customer's language, then `generateStructuredOutput` with `inquiryDraftSchema` (`{ reply, sourceArticleIds }`, `core/src/schemas/inquiry-draft.ts`) — only trusting `sourceArticleIds` that were actually in the retrieved candidate set (same don't-trust-the-model principle as 6.4's `productId` matching). Chained directly onto `classifyInquiry` (6.4/6.5) rather than a separate trigger: called only when the inquiry wasn't escalated, fulfilling 6.5's "no draft" contract. `classifyInquiry` now takes a third `language` parameter, threaded through from `POST /storefront/inquiries`. Verified live in English and Arabic: correct KB citation, draft written in the customer's own language, no draft for an escalated complaint, and a sensible generic draft (empty `sourceKbArticleIds`) when nothing matches. 
  - **Agent review workflow (6.7, shipped)**: `Message.draftStatus` (new `DraftStatus` enum — `PENDING`/`SENT_UNEDITED`/`SENT_EDITED`/`DISCARDED`, migration `20260721203902_message_draft_status`, mirrored in `core/src/schemas/inquiry.ts`) is set to `PENDING` the moment `draftInquiryReply` creates an `AI_DRAFT` message. Two new race-safe routes in `server/src/routes/inquiries.ts`: `POST /inquiries/:id/messages/:messageId/approve` (body: `{ message }`, reuses `addMessageSchema`) mints a new `STAFF` message with the submitted text — `draftStatus` flips to `SENT_UNEDITED` or `SENT_EDITED` depending on whether the submitted text differs (trimmed) from the original draft body — and `POST /inquiries/:id/messages/:messageId/discard` flips it straight to `DISCARDED` with no new message; both guard on `draftStatus: PENDING` via `updateMany` (404 if the message isn't an `AI_DRAFT` on that inquiry, 409 if already reviewed). The original `AI_DRAFT` row is **never mutated beyond `draftStatus`** — preserving `Message`'s immutability; the sent (possibly edited) text lives only in the new `STAFF` row. `GET /inquiries/:id` (and the two review routes' responses) resolve each message's `sourceKbArticleIds` into `{ id, title }` pairs server-side (`withResolvedSources` helper) — English title only, staff-facing, tolerates a since-deleted article by falling back to "Deleted article" rather than dropping the citation. - **KbArticle full-text search:** four generated `tsvector` columns (`search_en`/`search_ar`/`search_sw`/`search_fr`, added via hand-edited SQL in migration `20260721185241_kb_article_search` — Prisma's schema DSL has no native tsvector support, so `schema.prisma` declares them as `Unsupported("tsvector")?` purely so future migrations don't treat them as drift and propose dropping them; all actual reads go through raw SQL). Each column combines that language's `title` (weight `'A'`) + `body` (weight `'B'`) via `setweight`, falling back to the English field when a translation is missing so an untranslated article is still findable. One column per language (not one combined column with a language discriminant) since a query always knows the customer's language up front (`Inquiry.language`) and only ever searches one column. Postgres ships built-in text search configs for `english`/`arabic`/`french`; **Swahili has no built-in config** and falls back to `'simple'` (tokenize/lowercase only, no stemming) — a documented, accepted quality gap, not a bug. Query path: `server/src/lib/kb-search.ts`'s `searchKbArticles(query, language, limit?)` uses `prisma.$queryRaw`/`Prisma.sql` (Prisma Client can't express `@@`/`tsquery`/`ts_rank`, and `Unsupported` fields aren't selectable through it anyway) — the column name and `regconfig` are only ever taken from a fixed `Record<Language, string>` lookup (never raw request text), while the actual search text always goes through the tagged-template placeholder, never `Prisma.raw`. **Terms are OR'd, not AND'd**: `plainto_tsquery` ANDs every lexeme in the input, so a realistic multi-word customer question (many of whose words won't literally appear in a short KB article) matches nothing even when an article is clearly relevant — found live while testing 6.6. Fixed by taking `plainto_tsquery`'s already-stemmed/stopword-filtered output and replacing its `&` operators with `|` before re-parsing via `to_tsquery` (`replace(plainto_tsquery(...)::text, ' & ', ' | ')` — a standard trick for natural-language-input search), still only ever built from the fixed config lookup, query text still parameterized. This is retrieval plumbing for Phase 6.6's AI drafting (per `tech-stack.md`, "Postgres FTS to select candidate articles passed into the prompt, no vector DB until draft quality demands it") — there's a minimal ADMIN-only `GET /api/kb-articles/search?q=&language=` for verification, but deliberately **no search box in `KbArticlesPage.tsx`**, since FTS isn't an admin-facing feature here.
  - **Migration gotcha from the `Unsupported("tsvector")` fields**: `prisma migrate dev` (both plain and `--create-only`) replays the full migration history against the shadow database to compute a diff, and Prisma's diffing engine doesn't fully understand `Unsupported` columns that are `GENERATED ALWAYS AS ... STORED` — every subsequent migration attempt auto-generates spurious `ALTER COLUMN ... DROP DEFAULT` / `DROP INDEX` statements against the `kb_article` search columns, which fails against the shadow DB (`ERROR: column "search_en" ... is a generated column`) and would silently drop the FTS indexes for real if applied as-is. When this happens: review the autogenerated `migration.sql`, delete the spurious `kb_article`-related statements (keep only the statements for what you actually changed), apply the corrected SQL directly via `psql` against the real dev DB, then run `bunx prisma migrate resolve --applied <migration_name>` to mark it applied without re-running the shadow-DB diff. Seen first in migration `20260721190731_inquiry_ai_classification`. **This compounds on every subsequent migration** — since the previous migration's `migration.sql` was hand-edited after Prisma recorded its checksum, `prisma migrate dev`'s shadow-DB replay eventually fails hard enough to propose `prisma migrate reset` (**never run this** — it drops the entire dev database). When `migrate dev`/`--create-only` won't cooperate at all: skip it entirely — hand-write the migration directory (`mkdir prisma/migrations/<timestamp>_<name>`, matching Prisma's own SQL syntax/style) and its `migration.sql` from scratch based on the actual schema.prisma diff, apply it directly via `psql`, then `prisma migrate resolve --applied <name>`. Seen second in migration `20260721202737_message_ai_draft` (`MessageSender.AI_DRAFT` enum value + `Message.sourceKbArticleIds`).
